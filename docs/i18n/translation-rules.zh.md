# 翻译规则

[English](translation-rules.md) | 中文

本文约定如何在仓库内成对文档的两侧之间翻译。两种语言同权（[README.md](README.zh.md)）：一次变更可以用任一语言撰写，该侧就是这次更新的源，本规则约束如何产出或更新对侧文件。它同等人地约束人和 agent（智能体），agent 的日常翻译按术语指导一次完成改动内容。规则级别沿用 RFC 2119 用法：**MUST** / **MUST NOT** 由门禁或评审阻断；**SHOULD** 偏离时需说明理由；**MAY** 由执行者自行判断。

## 忠实性

- 对侧文件 *MUST* 说源侧所说的内容：不新增也不漏掉任何行为、前置条件、警告、版本声明或示例。若两侧在实质内容上不一致，任何语言都不默认胜出：先修正错误的一侧，再在同一变更中同步另一侧。
- 对侧文件 *SHOULD* 读起来是该语言的自然技术写作，而非逐词直译。翻译含义，按目标语法需要重组句子，保持作者的语体——原文简洁，译文同样简洁。
- 不要翻译不可译之物：若某句话因依赖源语言的习语而难以自然表达，翻译其含义，而不是移植习语。

## 语体

- 以目标语言母语技术作者的身份重述内容，而不是以译者的身份搬运句子，同时保留每个源子句：不增、不减——文笔流畅不能成为丢失子句的理由。
- 目标语言容易模糊执行主体时，为句子补出显式主体；中文里把含糊的被动句或抽象主语替换为实际主体（系统、门禁、评审人）。
- 优先使用目标语言既有的工程惯用语，而非仿译（如 false positive/negative 用误报／漏检），把隐喻本地化而非移植，目标语言需要时拆开名词链。
- 长段按语义单元拆分，一段一件事。段落边界 *MAY* 与源侧不同；结构签名不统计段落。
- 译为中文时，类别名词用中文并在首次出现括注英文（实操手册（cookbook））；译为英文时使用通行的英文类别名。字面的目录或文件引用保持代码体英文。

## 结构保持

配对门禁检查标题深度、围栏代码块、表格行列数、列表类型、有序列表起始编号、列表项数量、链接 locale 与语义目标。其余框架由人工保持；成对文件 MUST 在以下各项上逐一对应：

- 标题层级（层级相同、顺序相同——标题**文本**翻译），
- 列表形态与编号，
- 表格（列相同、行顺序相同；表头单元格按术语表翻译），
- 围栏代码块——**逐字节一致，包括注释**；配对签名比对它们的信息字符串与内容，
- 行内代码（命令、参数、配置键、文件路径、API 名、版本号）——原样保留，不翻译、不重排格式，
- 链接与锚点：每条相对文档链接 MUST 保持相同的语义目标，以及原样的 query/fragment 后缀。目标属于活跃双语语料时，英文侧使用其 `.md` 路径，中文侧使用其 `.zh.md` 路径；该语料内缺少对侧属于错误，语料外的目标保留原路径。外部 URL、图片与纯页内片段保持不变。语言切换行是显式的跨 locale 例外。链接**文本**翻译。

仓库既有的 Markdown 约定对 `.zh.md` 原样生效：每段一个物理行、相对链接可解析、结尾恰好一个换行。

## 术语

- [terminology.md](terminology.md) 是两个方向上的真源。翻译前先加载；每个已收录术语 MUST 遵循其所在行与“不要译作”列的禁止项。中文目标使用“中文”列及其“首次出现”括注；英文目标使用“English”列，不额外添加中文括注。
- 中文目标遇到未收录术语时，*MAY* 采用主流中文开源或厂商资料中的既有译法（K8s/Vue/MDN 中文文档、微软简中风格指南、大厂项目文档），并在变更中注明出处。没有先例时必须保留英文，并在「待定术语」下列出建议译法。
- 英文目标使用通行的英文术语。若源术语没有明确通行的英文对应，保留原词并给出简短说明，同时在待定术语中列出。任一方向都不得在正文中临时发明译法；定下的术语在同一变更或后续变更中写入 [terminology.md](terminology.md)。

## 排版

本节规则约束中文侧；英文侧遵循仓库常规 Markdown 约定。以下中英混排规则沿用 [MDN 简体中文翻译指南](https://github.com/mdn/translated-content/blob/main/docs/zh-cn/translation-guide.md)、[Kubernetes 中文本地化指南](https://kubernetes.io/zh-cn/docs/contribute/localization_zh/)、[Vue.js 中文翻译须知](https://github.com/vuejs-translations/docs-zh-cn/wiki/%E7%BF%BB%E8%AF%91%E9%A1%BB%E7%9F%A5) 与 [中文文案排版指北](https://github.com/sparanoid/chinese-copywriting-guidelines) 的跨项目共识，后者又基于 [W3C clreq](https://www.w3.org/TR/clreq/) 与 GB/T 15834—2011：

- MUST 在中文与拉丁词之间、中文与数字之间留一个半角空格：`每个 workspace 运行 2 个常驻服务`。全角标点与任何字符之间都不留空格。
- MUST 在中文正文使用全角（中文）标点：`，。：；？！（）「」`。半角标点只出现在行内代码内、被原样引用的完整英文句子内，以及数字中（`3.5`、`1,024`）。
- 中文正文 *SHOULD* 优先使用冒号、句号、逗号或括号，而非破折号。只有在其他标点都无法自然保持句子时才保留破折号。
- 顿号：并列项使用顿号（、），不使用逗号。
- MUST NOT 使用全角数字或全角拉丁字母——永远写 `123`，不写 `１２３`。
- 专有名词保持规范大小写：GitHub、TypeScript、ComfyUI——除引用代码外，不写 `github`/`Github`。
- 第二人称用「你」，不用「您」（与 Vue 与 Kubernetes 中文约定及本仓库的直接语气一致）。
- 强调标记（`**粗体**`、`*斜体*`）与源侧覆盖同一片段；中文没有斜体，渲染结果可能看起来相同——不要改用引号或其他装饰。

## 质量底线

- 双语文档完成的标志是：双语工程师只读其中任一文件，就能得到读另一侧所得的全部信息——同样的事实、同样的告诫、同样的语气，且没有多余内容。
- 运行 `pnpm verify-translation-pairing` 检查记录、切换行、标题深度、代码块、表格行列数、列表类型、有序列表起始编号、列表项数量、链接与仓库 Markdown 规则。列表与表格顺序、非规范列表编号、行内代码、强调、含义、术语与语气仍由人工评审负责。

## 参考

本规则引用的权威资料，供想了解背后理由的人和 agent 查阅：

- [中文文案排版指北](https://github.com/sparanoid/chinese-copywriting-guidelines)——中英混排空格与标点的事实社区标准。
- [MDN zh-CN translation guide](https://github.com/mdn/translated-content/blob/main/docs/zh-cn/translation-guide.md)——与本文形态相同的仓库内翻译规则文件；空格、标点与术语实践。
- [Kubernetes zh-cn localization guide](https://kubernetes.io/zh-cn/docs/contribute/localization_zh/)——最大规模 zh 本地化团队的术语首现与标点实践。
- [Vue.js docs-zh-cn 翻译须知](https://github.com/vuejs-translations/docs-zh-cn/wiki/%E7%BF%BB%E8%AF%91%E9%A1%BB%E7%9F%A5)——逐词条的译／留决策与语气。
- [zh-style-guide](https://zh-style-guide.readthedocs.io)——社区中文技术写作风格指南，本文借用其规则级分类（以及 RFC 2119 关键词级别）；该指南汇总 GB/T 15834/15835、clreq 与各厂商指南。
- [W3C clreq](https://www.w3.org/TR/clreq/) 与 [微软简中风格指南](https://learn.microsoft.com/en-us/globalization/reference/microsoft-style-guides)——正式的排版与厂商本地化基线。
- GB/T 19682-2005《翻译服务译文质量要求》——国家标准，其三项基本要求（忠实原文、术语统一、行文通顺）正是本文“忠实性”与“术语”两节的操作化。
