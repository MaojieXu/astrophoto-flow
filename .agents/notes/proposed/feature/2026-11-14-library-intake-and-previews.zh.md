# Agent Note: 导入在复制之前先固定身份

Status: proposed

[English](2026-11-14-library-intake-and-previews.md) | 中文

## Problem

导入是唯一同时决定文件身份、元数据和库内位置的时刻。旧仓库把这个时刻拆成枚举、登记、内容复制、元数据解析和预览生成，但它的任务记录、预检令牌和恢复规则散落在多个模块里。新仓库还没有导入管线，而一个天真的实现要么先复制再分配 id，要么等所有预览完成才显示任何东西。两种做法都会让部分失败变得昂贵：一个没有 id 的已复制文件无法安全重试，而一个因为某张预览失败就隐藏成功素材的批次，看起来就像数据丢了。

## Proposal

导入是一个基于不可变源列表的异步任务。任务把枚举、登记身份、复制并校验内容、解析元数据和生成预览作为独立阶段。后面阶段的失败永远不会抹掉前面阶段的成功。

### 入口

素材库接受文件和一层文件夹。选中的文件夹只贡献它的直接文件；不递归，也不要求预先授权的根目录。本地后端可以读取原生路径，浏览器可以把文件字节上传到暂存区；两条路径产生同一个任务和同一条素材记录。浏览器上传不是第二个素材库：暂存字节会被复制进托管素材库，发布后删除暂存副本。

### 预检

任务开始前，服务枚举选择、检查扩展名和可读文件头、汇总字节数、按分类分组，并返回一个带短期 `review_token` 的复核载荷。令牌绑定用户确认的确切源列表、分类、数据集意图和导入预设。提交不同的列表或已变化的源需要重新预检。CLI 可以跳过交互确认，但仍然拿到同一份复核载荷和令牌。

### 任务阶段

任务经过 `queued`、`running`、`cancelling`、`completed`、`completed_with_errors`、`failed`、`cancelled` 和 `interrupted`。每个条目经过四个阶段：

- **enumerate**：解析源、记录大小和修改时间、拒绝不支持的格式；
- **register**：分配 `asset_id`、读取文件头元数据，并发布一个 `availability = missing` 的待定素材；
- **content**：把源流式写入暂存文件、计算 BLAKE3、重新检查大小和修改时间，并原子发布库内副本；
- **metadata and preview**：解析 FITS/XISF 文件头并生成 100 像素缩略图。

先登记再复制是有意的：复制失败会留下一个已知的素材 id，可以重试，而不是一个孤儿文件。素材只有在内容阶段提交后才变成 `available`。内容失败和预览失败分开报告；预览失败不阻塞素材。

### 源冻结与重复

被接受的大小和 `mtime_ns` 是源契约。内容阶段在复制前后各检查一次；任何变化都会让该条目以 `SOURCE_CHANGED` 中止，并且不留下部分库内文件。重复检测只限当前任务：同一源路径出现两次会以 `DUPLICATE_SOURCE` 跳过。没有全局哈希去重，因为两次导入可以带着不同的分类或数据集意图。

### 格式与元数据

导入器识别 FITS（包括 fpack）、XISF、NumPy 数组、常见位图、相机 RAW 和视频/SER 容器。确切的扩展名列表只存在于一个模块，并由预检暴露。FITS 和 XISF 文件头用带版本的解析器解析；文件头不可读会把 `metadata_status` 标为 `failed`，但不会取消发布素材。分类绝不从文件名猜测：优先级是手动值、文件观察值、冻结的导入预设，最后是 `unknown`。

### 预览

每个素材都有一张最长边 100 像素的 JPEG 缩略图。数据集行复用第一个成员的配方作为组缩略图。显示预览和 FITS HDU 视图按需生成，永远不作为科学输入。预览失败会被记录并可重试；它不改变素材可用性，也不阻塞数据集。

### 取消、恢复与重试

取消会停止当前条目，并保留已完成条目。恢复从第一个未完成条目继续同一个任务。重试会创建一个带 `retry_of_task_id` 的新任务；如果原条目已登记但从未发布，则复用已有素材 id。调用方提供的 `request_id` 让重试幂等：同一个请求返回同一个任务，而不是启动第二次复制。

### 报告

任务报告分开 `registration`、`content` 和 `preview`。每个条目报告所处阶段、状态、已复制字节、哈希结果和错误码。只有每个条目都有终态阶段结果，批次才算完成；“登记完成”不等于“导入完成”。

## Alternatives considered

**在请求里同步导入。** 否决：大采集要花几分钟，浏览器会超时，而连接中断会让调用方无法知道复制是否发生。任务记录是唯一安全的核对方式。

**先复制，成功后再分配 id。** 否决：复制失败会留下一个无人跟踪的文件，重试也无法判断磁盘上的字节是否属于同一次导入。提前分配的 id 才是重试和回收站安全的前提。

**等预览完成再发布素材。** 否决：预览是派生数据。一张损坏的缩略图不应该隐藏有效原件，也不应该阻塞只需要文件的数据集。

**按内容哈希全局去重。** 否决：相同字节可以被导入两次，带着不同的分类、设备快照或数据集去向。全局去重会悄悄合并这些意图，并让删除变得有歧义。

**用文件夹监听代替导入。** 否决：监听器无法区分复制完成和仍在写入的文件，无法询问分类，还会在没有用户决定的情况下创建素材。文件夹监听以后可以作为导入任务的生产者加入，而不是第二个账本。

**对大文件使用 reference 导入。** 否决于托管复制决定：素材库必须拥有自己的字节。reference 导入会重新引入掉线的硬盘和外部修改。

## Acceptance criteria

- 一批文件加一层文件夹产生一个任务，每个被接受的文件一个素材；不会隐式遍历子目录。
- 每个条目分别报告登记、内容和预览结果，包括已复制字节和错误码。
- 源在预检和复制之间变化会以 `SOURCE_CHANGED` 失败，并且不留下已发布素材或部分库内文件。
- 预览失败后素材仍然可用，数据集仍然可导入。
- 取消任务保留已完成素材；恢复从第一个未完成条目继续；重试不会为同一条目创建第二个素材 id。
- 同一个 `request_id` 返回同一个任务，同一任务内同一源路径出现两次会以 `DUPLICATE_SOURCE` 跳过。
- 浏览器上传路径和原生路径产生完全相同的素材记录。
- 任何导入阶段都不在暂存区和托管素材库之外写入。

## Risks

- 包含 RAW、视频和 fpack 的格式矩阵会让文件头解析和缩略图生成参差不齐；预检必须报告“接受但预览不支持”，而不是让素材失败。
- 边复制边哈希在大批次上很吃 CPU 和 I/O；默认并发必须保守，并且可以按工作区配置。
- 杀毒软件和网络共享可能在复制后仍然占着暂存文件；原子发布需要重试和清晰的 `COPY_FAILED` 状态。
- 浏览器上传会临时复制一份字节；崩溃的上传必须由暂存清扫器清理，而不是留下一个隐藏的第二个素材库。
