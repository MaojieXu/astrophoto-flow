# Agent Note: 素材账本是原件的唯一记录

Status: proposed

[English](2026-11-14-managed-asset-ledger.md) | 中文

## Problem

旧仓库有素材表、数据集成员表、回收站账本和内容哈希，但也有 `storage_mode: reference|managed`。reference 素材只是一个路径加一句承诺：文件可能被移动、被覆盖，或者躺在一块已经拔掉的硬盘上。新仓库移除了引擎自己的素材账本，并让 HTTP 服务成为唯一写入者，所以剩下的账本必须说清楚它到底拥有什么。没有这个决定，“导入”可以指三件不同的事：复制文件、登记路径，或者把文件交给引擎并指望它的上传路由不会创建第二条记录。

## Proposal

每个导入的原件在成为可用素材之前都会被复制进素材库。没有 reference 模式，没有外部路径素材，也没有 `storage_mode` 列。源路径只作为审计文本保留，永远不作为读取位置。一个已登记素材拥有且只拥有一份库内副本。

### 记录

素材行包含：

- 登记时分配的稳定 `asset_id`；
- `name`、`original_filename`，以及作为审计文本的源路径；
- 相对于工作区数据目录的 `storage_location`；
- `blake3:<hex>` 形式的 `content_hash` 和 `byte_size`；
- `availability`，取值为 `available`、`changed` 或 `missing`；
- `revision`，从 1 开始，每次被接受的修改递增；
- 采集元数据：相机、光学系统、滤镜、ISO 或增益、偏移、曝光、累计曝光、传感器温度、binning、CFA 图案和帧分类；
- `value_sources`，逐字段记录 `manual`、`file`、`equipment` 或 `unknown`；
- 冻结的 `equipment_snapshot` 和采集快照；
- `calibration_status`（`UnCalibrated`、`Calibrated`、`Unknown`）和校准证据；
- `status`（`active` 或 `archived`）、备注和时间戳。

数据集归属存放在单独的行里，不在素材里。没有文件表，也没有版本表：重新处理一张原件会创建一个新素材，而不是旧素材的第二个版本。

### 身份与内容

`asset_id` 就是身份。重命名素材、编辑元数据、移动库内副本，或者把它加入数据集，都不会改变它。同一个源文件第二次导入就是第二个素材；账本不按哈希去重，因为两次导入可以带着不同的分类、归属或数据集意图。

库内副本通过暂存文件写入，边写边算哈希，然后原子移动到最终位置。哈希不匹配或复制失败不会留下已发布素材。任何科学读取之前，服务会重新哈希库内副本并与 `content_hash` 比较；不匹配就把素材标为 `changed`，读取以 `SOURCE_CHANGED` 失败。`changed` 或 `missing` 的素材仍然可见、可修复，但不能进入新的运行。

### 元数据与快照

元数据编辑是乐观并发的：每次修改都携带用户看到的修订号，过期修订返回 `409 REVISION_CONFLICT`，而不是覆盖另一个编辑。每个字段记录自己的值来自哪里。`unknown` 是一个值，不是零；缺失的数值字段不会存成 `0`。

设备在导入时按 id 关联，并冻结进素材。之后对相机、望远镜、滤镜或设备组合的编辑，永远不会改写素材的采集历史。快照记录的是图像声称使用的设备，不是设备库的实时视图。

校准状态由用户或导入预设声明，不由是否绑定了 Master 推导。绑定 Master 和执行校准是两件事。素材记录声明状态和证据，数据集记录当前绑定。

### 输入一致性

科学调用会声明 `input_mode`：

- `reproducible`：服务在调用前立即校验每个选中素材的哈希，不匹配就中止。如果调用需要更强的保证，它把选中的字节通过复制或 reflink 固定到运行目录，并把该路径交给引擎。
- `reference`：服务确认库内副本存在，然后原地读取。这个模式是显式的：它不承诺校验之后字节仍然不变。

因为所有素材都是托管的，旧仓库“把外部 reference 文件 materialize 到运行目录”的步骤消失了。`reproducible` 首先是校验保证，其次才是可选的 pin；它从来不是“引擎不可能读到被其他进程改过的文件”的无条件承诺。

### 引擎不得做什么

引擎的上传和保存路由可以为图暂存字节，但不能创建、重命名、移动或删除已登记素材、数据集成员或回执。HTTP 服务是账本的唯一写入者。需要库内文件的引擎路由，拿到的是服务选定的路径和调用快照；它拿不到工作区数据库。

## Alternatives considered

**保留 reference 模式并登记外部路径。** 否决：它省下一份文件，却放弃了素材库存在的两个属性——原件无法防止外部修改，素材库也无法作为一个整体备份或搬移。它还会让每个消费者重新面对掉线的硬盘、路径权限和修复流程。

**使用按哈希寻址的内容存储。** 否决：内容寻址是好的完整性机制，不是身份。重命名或重新分类素材不能改变它的 id，而同一份字节的两次导入完全可以是两个带着不同数据集意图的素材。哈希键还会让删除和引用计数更难，而不是更容易。

**允许一个素材下挂多个原件或版本。** 否决：一个素材就是一个已登记原件。文件变了就是一次新导入、一个新 id；处理结果是新素材。多原件会迫使每个数据集、校准绑定和回执都说明自己指的是哪个版本。

**保留引擎的素材账本和上传路由。** 否决：新仓库已经有意移除了那个账本。同一素材库上的两个写入者无法靠纪律变安全，而一个会登记素材的引擎上传路由会绕过修订检查和回收站状态。

**用软删除标记代替回收站账本。** 否决：素材上的一个布尔值记录不了移除的是哪条数据集归属、哪些文件已经清理、哪些条目失败。回收站需要自己的行和自己的生命周期。

## Acceptance criteria

- 导入文件会把它复制进素材库，记录 BLAKE3 哈希和字节数，并且不改变源文件。
- 成功导入后删除源文件不影响素材；重命名素材不改变 `asset_id`。
- 直接编辑库内文件后，下一次检查会把素材标为 `changed`，科学读取以 `SOURCE_CHANGED` 失败，而不是使用新字节。
- 过期元数据编辑返回 `409 REVISION_CONFLICT`，并且不覆盖更新的修订。
- API 和素材库视图能够区分 `unknown` 元数据与数值零。
- 任何引擎路由都不能创建或修改素材、数据集成员或回执。
- 把素材移入回收站不会删除库内副本；恢复后返回同一个 `asset_id`。

## Risks

- 托管副本会让大采集的磁盘占用翻倍，并给每次导入增加复制时间。素材库必须在批次开始前报告已复制字节和可用空间。
- BLAKE3 很快，但每次科学读取都哈希会给大数据集增加延迟；服务需要按路径、大小和修改时间缓存，并在任何写入时失效。
- Windows 路径长度、权限和杀毒软件锁会让原子移动比 Linux 上更不可靠；暂存和重命名路径需要重试策略和清晰的失败状态。
- 把“导入”理解为“给我的现有文件夹建索引”的用户会感到意外。导入对话框和 CLI 必须写明会进行复制，以及复制到哪里。
