# Agent Note: ComfyUI 管理器负责 bundle 安装

Status: proposed

[English](2026-11-14-comfyui-manager-owns-bundle-installation.md) | 中文

## Problem

旧工作台自己实现 bundle 安装：发现发布、克隆固定 Git 标签、校验 manifest、运行可执行文件的版本检查、加载适配器、记录安装回执，并通过原生确认流程暴露安装、准备、卸载和升级。新项目会适配官方 ComfyUI Manager。保留旧安装器会重复仓库发现、依赖处理、更新策略、确认、回滚和安全检查，并制造两份互不兼容的安装状态。

边界并不显然：管理器安装文件，但工作台决定图可以运行哪些 bundle 版本、哪些版本仍被引用。双方必须对安装目录、校验结果，以及图或调用仍需要某版本时移除该版本会发生什么达成一致。

## Proposal

ComfyUI Manager 分支负责安装。工作台负责校验、注册和执行。

### 管理器职责

管理器分支负责：

- 仓库和发布发现，包括 Git 及其支持的 registry；
- 安装、更新、移除和依赖安装；
- 用户确认界面及其警告；
- 下载、检出、回滚和部分安装清理；
- 安装目录及其文件。

bundle 安装到 `custom_nodes/<package_id>/`，根目录有 `bundle.json`。管理器不重写 `bundle.json`、不改字段名、不把它与管理器元数据合并。管理器专用的仓库信息留在管理器自己的目录中，不进入 bundle manifest。

引擎启动时启用管理器。已安装 bundle 目录是工作台校验器的数据；引擎不把它们当作 ComfyUI 节点模块导入。bundle 的 `__init__.py` 是无操作标记，不是节点注册。

### 工作台职责

工作台不实现 Git、发布发现、依赖安装、更新策略或安装回执。它不通过 HTTP、CLI 或 MCP 暴露安装、更新、卸载或准备。

工作台：

- 在启动时和每次管理器操作后扫描 `custom_nodes/*/bundle.json`；
- 按 bundle 契约校验目录；
- 把每个 bundle 记录为 `ready`、`invalid`、`incomplete` 或 `unavailable`，并带失败字段和描述文件哈希；
- 向画布和图校验暴露已安装 bundle 目录；
- 在图和调用中固定 `package_id`、`bundle_version`、`host_api` 和描述文件哈希；
- 拒绝运行固定组合不是 `ready` 的图。

工作台可以暴露只读的 `bundle_status` 结果和管理器界面链接。它自己不再提供安装按钮、版本下拉或“准备”动作。

### 移除与活跃引用

移除或更新 bundle 之前，管理器必须向工作台查询引用。工作台返回：

- 固定该精确 bundle 版本的保存图；
- 使用该 bundle 的活跃软件调用；
- 尚未到达终态的回执；
- 调用仍需要的已准备运行时目录。

工作台不可达时，管理器拒绝破坏性操作，而不是猜测。存在引用时，管理器列出它们并要求显式确认；它不在活跃调用下删除文件。

移除 bundle 永远不删除素材库素材、数据集、图或回执。固定被移除版本的图变为不可用并拒绝运行；它不会悄悄回退到另一版本。用相同 `package_id`、`bundle_version` 和描述文件哈希重装会恢复该图。

### 校验时机

管理器可能在工作台运行时安装或更新目录。工作台在管理器报告完成后校验，并在图运行前再次校验。写入一半的目录是 `incomplete`，不可运行。曾经 `ready` 然后消失的 bundle 变为 `unavailable`；活跃调用保留已解析路径并允许完成或失败，但不会开始新调用。

管理器和工作台共享一个安装目录；双方都不保留 bundle 文件的第二份副本。管理器目录可以记住可用版本，但工作台把文件系统和校验过的描述文件哈希当作事实。

## Alternatives considered

**保留旧工作台安装器，忽略管理器。** 否决：它重复管理器的仓库、依赖、更新、确认和回滚工作，而用户已经选择适配管理器。

**把管理器包在工作台安装 API 后面。** 否决：它为同一操作制造第二个 API 和第二个确认界面，工作台仍要跟踪管理器状态。直接的管理器界面加只读工作台状态更简单。

**让管理器同时校验和注册节点。** 否决：校验依赖工作台的节点 schema、适配器契约和图固定。管理器应安装文件，而不是决定图能否运行。

**让工作台保留发布目录，只用管理器下载。** 否决：两份目录会漂移，工作台仍要负责版本选择和更新策略。管理器拥有目录；工作台读取已安装描述文件。

**不询问工作台就移除 bundle。** 否决：管理器不知道哪些图或调用仍需要某版本，在活跃调用下删除可执行文件会把可恢复冲突变成失败运行。

**把已安装 bundle 目录当普通 ComfyUI 自定义节点导入。** 否决：引擎以禁用自定义节点运行，bundle 的 `__init__.py` 是管理器标记，不是节点实现。导入它会在适配器契约之外执行 bundle 代码。

## Acceptance criteria

- 管理器把 bundle 安装到 `custom_nodes/<package_id>/`，根目录有 `bundle.json`。
- 工作台不通过 HTTP、CLI 或 MCP 暴露安装、更新、卸载或准备操作。
- 工作台在启动时和每次管理器操作后校验已安装 bundle，并记录 `ready`、`invalid`、`incomplete` 或 `unavailable`。
- 图固定 `package_id`、`bundle_version`、`host_api` 和描述文件哈希；不可用版本拒绝运行。
- 移除或更新 bundle 前，管理器取得工作台的图、调用和回执引用；工作台不可达时管理器拒绝。
- 移除 bundle 不删除素材、数据集、图或回执。
- 部分安装目录是 `incomplete`，不可运行。
- 活跃调用可以带已解析路径完成，但 bundle 消失后不会开始新调用。

## Risks

- 管理器分支的 API 和目录约定可能变化。工作台必须依赖 `bundle.json` 和安装路径，而不是管理器内部。
- 两个状态所有者仍可能对版本意见不一。描述文件哈希和文件系统是工作台的事实；管理器目录只是参考。
- 管理器更新可能在工作台校验时替换 bundle。校验器必须读取稳定快照，并拒绝读取期间变化的目录。
- 管理器可能安装缺少 Python 依赖的 bundle。工作台只能标记 `invalid` 或 `incomplete`；它自己不能运行 `pip`。
- 管理器的确认可能比旧工作台的安装计划弱。必须写明信任模型和分支展示的警告。
- 用户可能期望工作台修复或回滚损坏的 bundle。工作台报告失败并链接到管理器；它不负责修复。
