# Agent Note: 前端 fork 逐字保留并冻结

Status: proposed

[English](2026-11-14-freeze-the-frontend-fork.md) | 中文

## 问题

前端是 ComfyUI_frontend 1.57.1 的完整副本：4507 个文件与上游逐字节相同，104 个被改，69 个新增。那 173 个文件里约有 30 条导入活不过一次升级，因为上游把共享组件挪进了 `@comfyorg/design-system`，把 API 客户端挪进了 `@comfyorg/api-client`。因此跟随上游意味着每个版本都要重做一次移植，而仓库里没有任何东西记录这些改动是为了什么。

## 提案

把这个 fork 作为钉住 commit 的逐字副本，不追踪上游。改为从内部缩小差异：凡是有扩展点能覆盖的改动，就把改动挪进 `src/platform/astrophotoflow/`，上游文件保持原样。需要在 1.57.1 上验证的四个扩展点是图读写、侧栏标签、节点定义刷新与执行状态。四个都成立，差异就会持续缩小；万一图或侧栏根本够不到，fork 就按现状冻结，我们不再假装它能缩小。

## 备选方案

**追踪上游，每个版本重新移植。** 否决：每次升级 30 条断掉的导入，换不来用户看得见的收益；我们的改动是集成，不是编辑器功能，上游也没有理由接收它们。

**用薄扩展加一份上游构建产物取代 fork。** 这是正确的终局，只被否决作为第一步：四个扩展点尚未验证，而一个够不到图或侧栏的扩展不是产品。

**用 submodule 加本地补丁。** 否决：173 个文件的补丁会随上游移动而腐烂，而完整副本加一份改动清单就能重建这棵树，不必为同一件事引入第二套机制。

## 验收标准

- 四个扩展点在 1.57.1 上全部可用，且不需要编辑任何上游文件。
- 我们的代码位于 `frontend/src/platform/astrophotoflow/` 下；剩余"改动加新增"文件数低于今天的 173，并随每次迁移而减少。
- `frontend/` 里没有我们自己的构建步骤；构建就是上游那一套加上我们的目录。

## 风险

- 安全与浏览器兼容性修复永远到不了；一次 Chromium 变更就可能打坏编辑器，而没有上游可合并。
- 我们撞上的上游缺陷只能改在 fork 里并记住，这正是改动清单的用途。
- 三年后再迁到薄扩展的成本未知，且必然高于今天，因为差异已经长大。
