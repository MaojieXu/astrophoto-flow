# Agent Note: 在人工路径之外增加脚本翻译路径

Status: implemented

[English](2026-11-13-scripted-translation-path.md) | 中文

## 问题

每个双语配对都由人工撰写：一次通写两侧，随后由配对门禁证明结构、切换行、链接与记录的哈希。这种写法可读性好，但每篇新文档都要付出评审级的力气；而 [translation-prompt.md](../../../docs/i18n/translation-prompt.md) 的提示词资产连同已评审的样例，没有任何调用方。没有调用方的提示词只是装饰：它漂移时不会有任何检查失败，读者也无从判断这份契约是活的还是摆设。

## 决定

[translate.ts](../../../scripts/translate.ts) 用术语表和三个已评审样例配对渲染该提示词，调用 OpenAI 兼容的对话补全接口，只取 `<final>` 段，修正语言切换行，再写出对侧文件。它从不记录配对，因为机器写出的译文尚未被人读过，而 `--write` 的含义仍是「有人确认过这份确切内容」。

凭据来自 `APF_TRANSLATION_*` 环境变量或永不入库的根 `.env`；缺少密钥时命令直接失败而不跳过，每次调用都在 `.artifacts/translations/` 写下记录，含模型、提示词路径与两侧内容哈希；[verify-translation-prompt](../../../scripts/verify-translation-prompt.ts) 加入门禁集合，使提示词资产与样例清单和其他契约一样受检查。

## 备选方案

**翻译完全保持人工。** 否决：门禁擅长结构、看不见文笔，因此每篇新文档仍要付出漫长的人工通写，而这部分本来也没有任何检查能验证。

**在 skill 里调用模型，而不是写成脚本。** 否决：skill 在 agent 会话中运行，没有固定提示词、没有重试策略、没有记录，同一篇文档两次运行可能结果不同，且什么都留不下来。

**由 translate 命令直接记录配对。** 否决：`--write` 现在的含义是「有人确认过内容」。由命令记录会让这句话失真，而门禁依然全绿。

## 结论

提示词资产及其样例有了调用方，一旦漂移就会让门禁失败。翻译一篇新文档变成：生成草稿、通读、修正、再记录。仓库里不放凭据也不放运行日志；封存归档不在范围内，因为它不是持续演进的翻译源。
